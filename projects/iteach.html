Case study 02 Cloud-native microservices

iTeach

Backend contributions to an AI-powered learning platform built by a larger team as cloud-native .NET microservices.

Role
.NET Software Engineering Intern
Company
ZioNet
Period
2026
Stack
C#, .NET 10, Dapr, PostgreSQL

01

The problem

Learners need a realistic sense of how long their work will take and how far they've come — and new users need a guided start.

iTeach already had an architecture, conventions and teams in place. My work was to add these capabilities inside that system, matching its contracts, boundaries and quality bar.

02

My responsibility

  • 01Duration estimationImplemented the logic that estimates how long an exercise will take.
  • 02Progress calculationsImplemented learner progress calculations.
  • 03Onboarding Todo systemBuilt an onboarding Todo feature across Manager, Accessor and Engine services.
  • 04Integration & qualityWorked with service contracts, API integration, testing, debugging and observability.

ScopeiTeach is a team-built platform. I didn't build its infrastructure or most of its services — this page focuses on my contributions within it.

03

My contributionsPlatform / team

The platform separates orchestration (Managers), business logic (Engines) and data access (Accessors). Services communicate through Dapr, which keeps service invocation and messaging consistent across the system. Features have to respect those boundaries: Managers coordinate, Engines compute, Accessors own data.

04

Engineering challenges

01

Fitting an established architecture

New code had to follow existing contracts, naming and layering rather than invent its own.

02

Numbers learners can trust

Duration and progress values need to be consistent and explainable, not just computed.

03

Contracts across services

A contract change ripples across services, so integration had to be deliberate and tested.

04

Debugging distributed calls

An issue can sit in any hop between services and sidecars, so observability matters.

05

The solution

  1. Model the feature in layersSplit the onboarding Todo feature into a Manager for orchestration, an Engine for its rules, and an Accessor for data access.
  2. Keep calculations in EnginesPlaced duration estimation and progress calculation logic in Engines, so it stays testable and reusable by Managers.
  3. Integrate through contractsWorked against defined service contracts and APIs, so other services can rely on predictable shapes.
  4. Test and observeVerified behavior with tests, and used Grafana dashboards and logs to trace and debug calls between services.

07

Outcome & lessons

Shipping inside someone else's architecture is its own skill — and a fast way to learn how well-designed systems stay that way.

  • Layering by responsibility (Manager / Engine / Accessor) makes features easier to place and review.
  • Contracts are the real interface between teams.
  • Observability is part of the feature, not an afterthought.
